# Core-flow contract

This document is the cross-repository contract for the Elera application flow.
The implementation is intentionally split between supervisor, CLI, and client
library. This file records the shared object and authorization semantics.

## Resource identity

Applications, app-admin tokens, databases, identities, SQL credentials, runtime
tokens, and operations have Snowflake IDs. Friendly names are labels only.
Physical database and SQL-user names are generated by the supervisor from those
IDs and are not selected by applications.

## Token resolution

An app-admin token is scoped to exactly one application and may manage only its
application resources. A runtime token resolves directly to:

`application + database + identity + scopes`

Each runtime token represents one database context. An application that needs
two databases uses two runtime tokens. Keep the root token out of application
workloads.

Each API token maps to its own MariaDB account. The account has a separate
password and grants that match the token's role and database scopes. The server
stores the password in encrypted metadata. The routing bundle returns the
account credentials after the API token authenticates. Create the root account
during initialization and grant it access to every database, with `elera_meta`.

## Application contract

Applications configure only:

```text
ELERA_API_ENDPOINT
ELERA_API_TOKEN
```

The client library obtains the routing bundle and physical SQL credentials
using that token. Applications do not provide application, database, identity,
SQL username, SQL password, node, or cluster settings.

## Routing bundle

The supervisor returns application, database, identity, resource IDs, token
credentials, writer, readers, failover nodes, bundle version, expiry, node
identity, and port data. Routing changes use the WebSocket event stream. HTTP
API bundle retrieval provides recovery.

## Authorization boundary

Root-only operations include initialization, bootstrap, recovery, node
lifecycle, draining, cluster configuration, secrets, and platform backup or
restore. App-admin operations are small to application resources, with
databases, identities, runtime tokens, routing inspection, and application
telemetry.

## Supervisor endpoint matrix

Supervisor-generated bundles require `apiVersion: "v1"`, integer TCP ports
from 1 through 65535, and both `routes.primary` and `routes.balanced`.
Route `nodeId` is optional metadata. `nodeIdentity` is a required string and
`refreshAfter` is optional. Runtime token creation requires an explicit scopes
array. No runtime scopes are implied by identity purpose.

- `POST /api/v1/applications`: root-only application creation by friendly name.
- `GET /api/v1/applications/:applicationId`: application status by stable ID.
  root or the application-bound `app:admin` token.
- `POST /api/v1/app-admin/tokens`: root-only app-admin token creation.
- `POST /api/v1/databases`: database provisioning.
- `POST /api/v1/databases/:databaseId/delete`: database deletion by stable ID.
  accepts `dryRun`, `confirm`, and `idempotencyKey`.
- Migration uses a CLI workflow. Initialization and reconciliation use separate APIs. There is no
  standalone migrate endpoint.
